# v3.4.0 targeted hardening

## Offline claim coverage

After contradiction and required-qualifier checks, offline verification compares
the claim's unique alphabetic tokens of at least four letters with the matched
source's verbatim text, keywords, required qualifiers, and PICO fields. It excludes
the existing role-binding stopwords and the generic verbs `evaluated`, `treated`,
`received`, and `administered`. Coverage below 75% produces `partially_supported`
with the unverified terms in its diagnosis. Coverage at 75% passes this check.
No endpoint-specific synonym or promotional keyword lists were added. Live claim
verification now receives the authorized source passages explicitly, including
when no reference cache is available.

## Signed session routes

`POST /auth/token` accepts:

```json
{
  "tenant_id": "tenant_demo",
  "actor_id": "cams_requester",
  "role": "requester",
  "ttl_seconds": 3600
}
```

It returns `access_token`, `token_type` (`Bearer`), the normalized identity and
role, and `expires_in`. Role and lifetime default to `requester` and 3600 seconds.
Allowed roles are `requester`, `service`, `reviewer`, and `approver`; surrounding
whitespace is removed, and unknown or blank roles return 422. Requester and
service tokens cannot accept edits in hosted mode. Request reviewer or approver
authority deliberately for the authenticated individual performing an acceptance.
Send the token in `Authorization: Bearer <token>`.

The lifetime must be a positive integer. Hosted issuance rejects a lifetime above
3600 seconds with 422. `MLR_GENIE_MAX_TOKEN_TTL_SECONDS` may set the cap to an
integer from 1 through 86400; invalid configuration refuses startup. The
default requested lifetime stays 3600, so a cap below 3600 requires callers to
request an explicit shorter lifetime; omitting it returns 422. Local development retains positive
lifetimes without this upper cap. Rotating `MLR_GENIE_SESSION_SECRET` revokes
every outstanding token. The cap does not shorten tokens already issued; rotate
the signing secret at rollout to invalidate older long-lived credentials.

Set **`MLR_GENIE_ENV=hosted` in every deployment**. Unset or blank mode also
resolves to hosted unless the local opt-in below applies. Startup refuses a missing,
blank, shorter-than-32-UTF-8-byte, or published-default `MLR_GENIE_SESSION_SECRET`.
An unknown environment mode also fails closed. Hosted job, artifact, integration,
and evaluation routes always require signed bearer tokens, even if
`MLR_REQUIRE_SIGNED_BEARER_TOKEN=false`. Identity headers and artifact query
parameters cannot authenticate. Signature, expiry, tenant, and actor checks remain.

Hosted CORS defaults to no allowed browser origins. `MLR_GENIE_ALLOWED_ORIGINS`
accepts comma-separated exact HTTP(S) origins; wildcard and malformed origins
are rejected. Cookie credentials are disabled. CAMS and CommsRx server calls
need no CORS allowance.

For local development with mode unset, set `MLR_GENIE_ALLOW_LOCAL=true` and run
`python -m backend.server --host 127.0.0.1 --port 8000`. The launcher binds the
socket first; only its actual loopback address enables implicit local mode.
A public bind or an unknown bind address stays hosted, including a generic ASGI
server whose bind address is not registered by this launcher. Explicit
`MLR_GENIE_ENV=local` retains prototype behavior for deliberate development use.
Cloud Run's `K_SERVICE` marker always selects hosted mode; combining it with
explicit local mode refuses startup. Startup logs the resolved security mode.

Local mode retains the optional `MLR_REQUIRE_SIGNED_BEARER_TOKEN=true` switch.
One startup warning names each relaxed signing-key, issuer, legacy-authentication,
and CORS setting without printing secrets. Keep local mode confined to development.

When `MLR_GENIE_BOOTSTRAP_SECRET` has a nonempty value, `/auth/token` requires a
matching `X-MLR-Bootstrap-Secret` header. A missing/empty header returns 401 and a
mismatch returns 403; comparison uses `hmac.compare_digest`. The secret is read
on every request, so rotation takes effect without a restart. Supply it securely
through the process environment and the header, never through URL parameters.
In hosted mode, missing/blank bootstrap configuration returns HTTP 503; the issuer
never becomes open. If unset or empty in local mode, prototype issuance remains.

The issuer still signs caller-supplied identities: holders of the bootstrap
secret can choose the tenant, actor, and role. Restrict the issuer to a trusted
service; the shared secret does not replace per-user identity verification.

## Reviewer identity and stored acceptances

Accepting edits requires a signed token with role `reviewer` or `approver`, whose
`actor_id` identifies the actual reviewer. A `requester` or `service` token may submit evidence,
pending comments, and rejected comments, but cannot create an acceptance through
CommsRx `acceptedEdits`, accepted comments, `/jobs/{id}/comments`, or nested intake
comments. Unknown roles also lack acceptance authority. Local legacy-header
acceptance remains available only in local mode.

Authorization is recorded by the server against the exact comment/edit content.
Imported job metadata and placement flags are not trusted as approval. Hosted
application and rendering verify stored authorizations, including already-placed
edits. Historical acceptances without these records require explicit reviewer
reacceptance. Signed-token rotation does not erase stored acceptance provenance.
An unchanged pending reimport or a later service-triggered execution preserves
the accepting person's `human_actor` and OOXML author; revision actors separately
describe who executed the operation.

## Hosted deployment and artifact isolation

Azure-hosted CAMS and CommsRx use the global external HTTPS Application Load
Balancer in `deploy/terraform/https.tf`. A regional serverless NEG connects it to
Cloud Run while ingress remains `INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER`.
Supply a controlled `public_host`; a Google-managed certificate terminates TLS
on that hostname. Cloud Armor throttles `/auth/*` at 60 requests per minute per
source IP and `/integrations/*` at 600, returning 429 above those approximate
limits. Callers sharing an Azure outbound IP share those limits.

Cloud Run grants `allUsers` invoker permission so the load balancer can forward
the application's MLR bearer token. Hosted application authentication still
protects integration, job, and evaluation routes; retaining the ingress restriction
blocks direct Internet access to the Cloud Run URL. See the
[Terraform deployment guide](../deploy/terraform/README.md) for APIs, IAM,
DNS, certificate readiness, and external verification steps.

Production deployment remains a separate authorized step. After deployment,
verify `/health` returns 200 from outside Google Cloud and tokenless CAMS
verification returns 401. Run `evals/live_integrations.py --base-url https://<host>`
with the deployed bootstrap secret supplied securely. Its synthetic fixture
checks requester verification and refusal of omitted-role acceptance. Record the
public hostname, immutable image digest, and a separate successful requester
verification with a real journal PDF and a reworded claim. Local hosted-mode
evaluation does not establish public reachability or that deployment evidence.

Terraform sets hosted mode, signed authentication, and an empty origin allowlist.
It creates `mlr-genie-session-signing` and `mlr-genie-bootstrap` Secret Manager
containers and grants the runtime identity access to those secrets. Cloud Run
uses `secret_key_ref`; Terraform manages metadata and references, never secret
version payloads or secret values in state.
Populate versions through your secret-management process before rolling out the
service. Supply `app_image` as the immutable digest of an image built from this
fix; the template no longer silently deploys the old `3.0.0` image.

Artifact directories retain portable existing job IDs. Other IDs use a dedicated
SHA-256 namespace, preventing identifiers such as `victim_job` and `victim:job`
from sharing files across tenants. The ambiguous legacy directory for an unsafe
ID is deliberately not read; re-upload/regenerate those artifacts after upgrade.

If SQLite initialization raises `sqlite3.OperationalError`, the store logs a
warning and retries once at `Path(tempfile.gettempdir()) / original_filename`.
Failure there propagates. Temporary storage is not guaranteed to survive cleanup
or machine replacement; use a SQLite-compatible persistent path for durable data.

## Approval-day label diffs

`POST /jobs/{job_id}/diff-label` uses the existing tenant authentication checks.
It accepts `prepared_scenarios`, `final_approved_label`, and `launch_kit_assets`.
Scenarios and assets default to empty lists; when assets are omitted or empty,
the route checks the job's latest revision.

```json
{
  "final_approved_label": {
    "section_12_1_moa": "The agent binds a receptor.",
    "section_14_clinical_figures": [
      {"endpoint": "response", "old_value": "20%", "new_value": "25%"}
    ]
  },
  "launch_kit_assets": [
    {"asset_id": "brief", "body": "The agent binds a receptor. Response was 20%."}
  ]
}
```

Section 12.1 checks the required wording ignoring case and whitespace. Section 14
flags a retained old value, with boundaries to avoid matching it inside another
word or number. An asset need not repeat every new figure; an absent old value
does not itself require an update. Identical old/new values are ignored.
Prepared scenarios must cover the supplied section changes to count as a match.

These deterministic checks form Layer 1. `GeminiGateway` then sends the changed
sections, prepared scenarios, and asset claims in one schema-constrained call.
The response must cover every section/asset/claim combination. Application code
checks each claim against its supplied asset and each label quote verbatim against
the approved section text (excluding superseded values). Model-only impacts are
merged with the deterministic findings; proposed wording requires human approval.

`label_delta` includes `layer_one_affected_assets`, `model_assessment`,
`label_quotes_verified`, `used_live_sdk`, and `telemetry`. Set `require_live: true`
on the request or `MLR_REQUIRE_LIVE_GEMINI=true` in the environment to require live
assessment even without configured credentials. Configuring a provider/client
already requires live assessment. Provider failures, empty/invalid output,
unverifiable quotes, and incomplete coverage return HTTP 502 with
`assessment_failed: true`; they never produce a successful local-only response.
Offline mode remains explicitly identified by `used_live_sdk: false`.

The response includes `label_delta`, `job_id`, `tenant_id`, and the updated job.
The analysis is saved in `job.metadata.last_approval_day_label_delta`; asset text
is not modified. The tool is also registered on `genie`.

## Human decisions and safety extraction

Comment reconciliation supplies complete comments to Gemini and validates returned
comment IDs. Human accepted/rejected decisions cover the known versions of the
comments on that target. Server-recorded resolution history survives storage and
reimports; new or changed conflicting comments reopen review. The authenticated
actor owns the decision. Accepted edits use the existing atomic placement and
OOXML writers, producing both the revised copy and real deletion/insertion markup.

Intake and DOCX upload use a structured claim/safety extraction schema over the
complete copy. Every cited span, including patient/product/event evidence, must
exist verbatim before any finding is stored. Verified findings include offsets
and a source hash; repeated findings are merged. Safety statements and extracted
claims enter active review (`in_review`) and claims skipped by the offline
paragraph filter are included. Individual adverse-event narratives enter CV-08
`hold` before creation of communications revisions, with actionable findings and
routing instructions. Model proposals never become human-confirmed facts.

Safety, label, and comment receipts are retained in
`job.metadata.assessment_telemetry_receipts`; claim-verification receipts remain in
`job.metadata.telemetry_receipts`.

## SDK model resolution

Only clients whose actual type's module starts with `google.genai` receive these
transport model IDs:

| Logical role ID | SDK model ID |
| --- | --- |
| `gemini-4-argon` | `gemini-3.1-pro-preview` |
| `gemini-3.8-flash` | `gemini-3.8-flash` |
| `gemini-3.5-flash-lite` | `gemini-3.5-flash-lite` |
| `gemini-embedding-2` | `gemini-embedding-001` |

The original 2.5 mapping returned live 404 responses for this account. The
replacements above were checked against the authenticated model catalog on
October 30, 2026. Deep review and PV gating were tested with unmocked SDK calls;
orchestration and embeddings were not invoked by that workflow. `gemini-4-argon` is also in the
catalog, but it does not advertise `createCachedContent`; deep review uses the
cache-capable `gemini-3.1-pro-preview` transport.

Generation, interactions (including cache retries), reference caches, and
embeddings use the resolver. Mock clients, offline mode, and unknown IDs retain
their original behavior. Telemetry `model` and cache `model` preserve logical
roles; `effective_model` records the SDK model ID. Claim receipts use that actual
ID for live requests. The live workflow and its verified results are recorded
in [the live verification report](live-verification-2026-10-30.md).

For a real SDK request using `cached_content`, the per-turn task instruction is
included in the input text. The cached content supplies its existing system
instruction; sending another `system_instruction` in generation config produces
HTTP 400. If a cache must be retried without caching, the router restores the
ordinary generation system instruction.
