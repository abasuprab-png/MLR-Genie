## Verdict
Worth pursuing as an assisted communications preparation/review product. The supplied genuine DOCX/PDF package is meaningful progress. It is not yet trustworthy to present a green supported verdict as validated evidence, or to host confidential multi-client jobs. These issues matter even with a human approving: stale evidence and false reassurance make the human's review harder rather than saving time. Prioritize trustworthy reviewer handoff, not additional features.

## Findings
1. **P0 before shared/client hosting: authentication is caller-controlled.** `backend/main.py:146–193` accepts tenant/actor headers or any nonempty Authorization value; it never verifies credentials and falls back to the requested job's tenant. Independent in-process HTTP GET to `/jobs/victim-private` returned 200 and tenant `victim` for `X-Actor-Id: attacker` alone and independently `Authorization: nonsense`. Reviewer provenance is therefore not identity assurance. Existing auth fixtures only check no headers and an honestly conflicting tenant header (`evals/audit_adversarial.py:201–237`). Fix with verified principal, server-derived tenant/roles, and denial tests for spoofed/missing/expired tokens. A trusted gateway could compensate only if actually deployed, stripping/validating these headers; that is not established by this package.
2. **P0 reviewer correctness: evidence stays on old wording after accepted edits.** `backend/tools/document_tools.py:103–170` appends a changed revision without invalidating/rechecking claims. `backend/main.py:844–847` checks/annotates evidence before edits, and `:854–861` packages afterward. `backend/document_engine.py:1490–1495` exports current version with old claims. Reproduced `Aurenix improved overall survival` → accepted `worsened` edit: current version 2 says worsened, claim remains original improved and supported. This matches supplied v2 matrix's old wording. Fix by version/hash binding each assessment, invalidating on changes, rechecking changed claims after applying edits, regenerating annotations/matrix; export must refuse or clearly label stale assessments.
3. **P0 claim confidence: offline fallback silently certifies clear meaning changes.** Four independent source→claim changes returned `supported` / `Within Approved Meaning (Ready for MLR Review)`: adults→children; increased→decreased overall survival; 24 weeks→24 months; response60%/toxicity20%→response20%/toxicity60%. `document_tools.py:278–379` fills absent PICO fields from source/default labels; `:583–651` compares numbers as sets and same-spelling units, not quantities bound to endpoints; `:670–734` checks comparator/endpoint/qualifiers but absence of a detected conflict becomes supported. Real PDF extraction initializes required_qualifiers to [] (`document_engine.py:788–796`), so this is relevant beyond specially hand-authored source metadata. This is an offline-path finding, not evidence that a live model makes those same mistakes. But current demo operates offline, and model availability must not turn heuristic matching into a certified verdict. Fix with unknown/partial for unproven dimensions, explicit population/direction/timeframe checks and endpoint-value-unit linkage; preserve omission versus contradiction. Add these unseen probes plus clean valid controls.
4. **Provider/privacy assurances remain unverified.** `document_tools.py:414–441` reports zero_data_retention from configuration rather than provider proof; offline router returns supplied fallback (`models_router.py:378–389`). The review package's offline telemetry is honest about transport, but does not validate real model identifiers, live service behavior, privacy setup or production end-to-end operation. Validate separately only with authorized sanitized input and provider/account evidence.

Then run a small blinded sanitized communications workflow with real Word source, PDF evidence, authentic accept/reject/edit decisions and one deliberate numeric/population change. Reviewer should navigate every claim to exact support, see uncertainty, and get a correct clean/redline/package. Compare total prep-plus-review time and corrections against manual baseline. Report known fixture successes separately from unseen challenge performance and observed minutes saved. Keep human release control.
